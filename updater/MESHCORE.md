# MeshCore command interface (XIAO nRF52840 + Wio-SX1262)

An optional layer that lets an operator drive the updater over LoRa using
MeshCore direct messages. The Nordic BLE DFU implementation is unchanged; this
layer only decides *when* a DFU may start and reports what it does.

**Status: host-tested, builds and links, not yet run on hardware.** See
[Known limitations](#known-limitations) before trusting it near a real drone.

## Build

```sh
./build-meshcore.sh            # = MC_WIO_SX1262=1 ./build.sh nrf52, own build dir
```

Output goes to `updater/build_xiao_ble_nrf52840_meshcore/`. Without
`MC_WIO_SX1262` the build is the stock one and none of this is compiled in.

Flash: the image uses 387,844 of 388,970 bytes of slot0 (about 1.1 KB spare).
To make room, `boards/meshcore/xiao_ble_wio_sx1262.conf` turns off the mcumgr
echo command and lowers BT / BT-connection log verbosity from INF to WRN. If
you add features and overflow, the next lever is `CONFIG_USB_DEVICE_STACK=n`
(builds at ~367.6 KB) at the cost of the USB console and 1200-baud touch; UF2
double-tap and OTA over BLE still work.

## Wiring (Wio-SX1262 on XIAO nRF52840)

| Signal | Pin   | Signal | Pin   |
|--------|-------|--------|-------|
| NSS    | P0.04 | BUSY   | P0.29 |
| RESET  | P0.28 | DIO1   | P0.03 |
| RXEN   | P0.05 | SPI    | spi2 (P1.13/14/15) |

`i2c1` is disabled by the overlay because it shares P0.04/P0.05.
**Never transmit without the antenna attached.**

## Provisioning

1. Put the operator's 64-hex-character MeshCore public key in
   `updater/boards/meshcore/operator.conf` (git-ignored):
   `CONFIG_MC_OPERATOR_PUBKEY="<64 hex>"`
2. Build and flash. On first boot the node generates its own identity and logs
   `MeshCore node public key: <hex>`. Add that contact in your MeshCore client.
3. Send direct messages to the node. Radio defaults are the MeshCore US preset
   (910.525 MHz, SF7, BW 62.5 kHz, CR 4/5); change them in Kconfig (`MC_*`).

With an empty operator key every privileged command is refused (and a warning is
logged at boot).

## Commands

One line per message; the command word is case-insensitive; extra words are an
error, not ignored.

| Command | Privileged | Meaning |
|---|---|---|
| `status` | no | State, armed target, DFU progress |
| `scan [page]` | no | BLE advertisers heard, strongest first (first scan after boot may be empty) |
| `rssi` | no | Live gate state for the armed target |
| `arm <AA:BB:CC:DD:EE:FF> <bundle> [random\|public]` | **yes** | Select target and bundle (bare file name) |
| `disarm` | **yes** | Clear the armed target |
| `start` | **yes** | Begin DFU, only if the gate is READY |
| `abort` | **yes** | Stop a running DFU |
| `version` | no | Firmware version |
| `battery` | no | Battery voltage |
| `log [page]` | no | Recent events, newest first |

Privileged commands are accepted only from the configured operator public key,
with replay protection (persisted timestamp counter).

## START gate

`start` is refused unless **all** hold:

- the BLE advertiser matches the armed address **exactly** (six octets and
  address type; no name, prefix or wildcard matching);
- RSSI has stayed at or above `CONFIG_MC_RSSI_MIN` (default -75 dBm)
  continuously for `CONFIG_MC_GATE_HOLD_MS` (default and minimum 5000 ms), with
  no gap over `MC_GATE_MAX_GAP_MS` and at least `MC_GATE_MIN_SAMPLES` adverts;
- the device is armed (arming expires after `MC_ARM_TIMEOUT_S`).

A single weak sample restarts the window. The RSSI threshold is build-time only.

DFU never starts on its own: with `CONFIG_MC_CMD_ENFORCE` (default y) the
upstream auto-flash-on-boot path is disabled, and all three DFU start paths
(auto flash, SMP trigger, runner API) require a one-shot 2 s permit that only a
passing `start` grants.

## Progress reports

Milestones are sent at 0 / 25 / 50 / 75 / 100 % plus success or failure, as
MeshCore messages to the operator.

## Code layout

- `src/mc/` portable core (gate, command grammar, controller, wire format,
  crypto, identity store, ...) with no Zephyr dependency; `mc_zephyr.c`,
  `mc_radio.c`, `mc_permit.c` are the Zephyr glue and SX1262 driver.
- `src/mc/ed25519/` vendored Ed25519 (size-reduced variants selected by
  `MC_ED25519_SMALL`, cross-checked against the reference implementation).
- Upstream edits are small: a status observer in `dfu_status.*`, an advert
  observer in `ble_scanner.*`, the permit check in `dfu_runner.c`, init and the
  auto-flash gate in `main.c`, and conditional wiring in `CMakeLists.txt`.
- Host tests: `cd updater/mc-tests && make test` (18,296 checks, including
  vectors generated by MeshCore's own code).

## Security model

- Privileged commands: operator public key only, signed/encrypted per MeshCore,
  replay-protected. Unprivileged commands are read-only.
- Secrets (operator key, replay counter, identity) are **not** kept on littlefs,
  because the SMP file service can read/write any path. The identity lives in a
  dedicated 4 KB flash page (`mc_identity_partition`, 0xF3000).
- The operator key is compiled in; rotating it means rebuilding.

## Known limitations

- **Not run on hardware.** The SX1262 driver (SPI, TCXO, TX/RX, listen-before-
  talk) and the full flow have only been compiled and host-tested.
- LoRa / BLE coexistence is unverified.
- The 4 KB identity page at 0xF3000 is assumed free and not erased by a UF2
  flash; a power cut during identity-page rollover can lose the identity (it is
  regenerated, which changes the node key).
- A bundle swapped over SMP between `arm` and `start` is not detected.
- The 2 s permit has a small race window.
- A badly wrong operator clock can lock the operator out via the persisted
  replay timestamp.
- Flash headroom is ~1.1 KB; see Build.
